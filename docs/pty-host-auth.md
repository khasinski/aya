# PTY host socket authentication - design and implementation

I base this branch, `pty-host-socket-auth`, on main `ead520c8` (merged B4 and rules PR1, #232). Justyna chose the in-memory capability on 2026-10-16. The persistent-capability proposal and its measurements below are historical and superseded; [the memory implementation note](pty-host-auth-memory.md) records the reviewed stages.

## Current state

Main creates a random32-byte capability only in memory after the verified-gone creation guard permits a new host. It passes that capability only through inherited FD5; the host never creates or reads a capability file. The generic persistent creator/reader has been removed. Existing `pty-host-auth/key` artifacts are ignored, neither read nor repaired/deleted, even when an artifact contains the exact key of a surviving development host.

New hosts refuse every pre-auth application RPC/event, including the read-only pane-state observer from #232. That observer borrows main's in-memory capability and authenticates through the same opener, without starting a host or owner. Normal quit, after existing vetoes, may announce one bounded single-use transfer. Planned B3 updates reserve that same exclusive purpose/attempt slot before freezing readers, publish asynchronously, and preserve their separate reader/lease commit and verified-old-JS-exit boundary. B4 can recover a host only when this main started it or adopted validated continuity through an announced transfer.

A new main after an unannounced crash/force quit has no capability and cannot adopt a surviving host. It uses retained private inventory and identity-bound stop consent; Cancel keeps processes and input stays disabled. A valid proof from an announced recipient that meets a still-closing previous main gets authenticated principal-busy, opens the window without a stop question, and retries within10s. A verified live socketless host gets up to3s shutdown grace; unknown/alive creation proofs never authorize unlink/start. Released pre-auth v0.12.0 hosts retain their strictly bounded identity-bound read-only migration probe and report labels; their replies never supply signal authority.

## Proof and its boundary

The capability proves possession, not that the executable is Aya. It never enters argv, pane environments, logs, renderer IPC, registry or checkpoint state. The native-owner key remains separate and memory-only. There is no persistent capability lookup, no silent rotation on authentication failure, and no native protocol/binary change.

An authorized quit writes only a fresh nonce, purpose/attempt, deadline and host PID/start identity in a private0600 one-use ticket. Ordinary publication has one parent monotonic2s budget; the host checks both monotonic lifetime and wall expiry, at most120s. Publication is asynchronous and the reserved window is inert until in-budget activation. The new main consumes the ticket once and redeems it on the bound kernel host/recipient identities; one recipient is committed before credential release. Only validated owner continuity plus its exact completion ACK permits rearm. Cancel, expiry, lost replies and late IO cannot undo a committed recipient or silently grant a second transfer.

The remaining exposure is explicit: a same-UID process able to read that short-lived ticket can race to become its first recipient. Root, process-memory inspection and a compromised authorized main/host are also outside the boundary. This is not an OS sandbox or executable-identity broker. Ordinary configuration readers without such a live ticket or memory access cannot obtain the new host capability. Earlier persistent-capability development hosts retain their original exposure until explicitly retired; ignoring their files does not retroactively revoke them. Unsafe/missing/expired/wrong-host tickets and failed proofs preserve processes and use the existing consented fallback, never implicit start or signal.

## Authenticated connection

Connections use a bounded mutual HMAC-SHA256 handshake before normal JSON RPC. Client and host each contribute a fresh 32-byte nonce. Domain-separated server/client proofs cover both nonces, protocol version, host instance and kernel peer PID/start identities; proofs from another connection, role or host cannot be replayed. The main verifies the server proof before sending its client proof. Both sides require same-UID kernel peer identity, constant-time proof comparison, a small closed schema (at most 1 KiB per handshake frame) and a five-second whole-handshake deadline. Missing proof, wrong proof, malformed/oversized input or expiry closes that connection with a fixed error, without affecting live panes. Pending unauthenticated connections and their buffers have aggregate caps and do not keep an empty host alive indefinitely.

The host must not add an unauthenticated socket to its broadcast recipients, send initial spawned/snapshot/replay/exit events, or dispatch any ordinary request. Without authentication it refuses read/search/replay, write, resize, spawn/prepare, kill/shutdown, exit/display acknowledgements, composer metadata, every handover operation (including announce and claim), version and status. Only the minimal handshake/version-of-auth-protocol envelope is public; it contains no pane data, owner key or work status. Pipelined RPC cannot race authentication. Authentication errors never trigger socket unlink, host spawn, owner replacement or a legacy downgrade.

One active main principal is bound to PID plus kernel start identity; its sockets may reconnect. A different authenticated principal cannot take control while it is still live or its identity is uncertain. After the old main is proved gone, the relaunched main may become the principal. A second connection must not invalidate the first merely by sending a bad proof. All RPC paths to new authenticated hosts, including handover claims and explicit restart, use the same handshake. The bounded, identity-verified released-host migration probe described below is the only legacy read-only exception; it sends no secret and grants no stop authority. Socket discovery may read only the kernel peer identity without sending an RPC or either credential. Existing identity-bound stop consent is still required after authentication.

## Ordinary relaunch and B4 key continuity

After a real ordinary-quit announcement, a new main consumes/redeems the one-use ticket, proves possession to the same surviving host, and validates its complete bounded owner/pane/generation manifest before enabling B4. Reads continue during ordinary transfer: there is no checkpoint or output freeze. Successful adoption retains process PIDs; it does not restore screen/history a dead JS host had already consumed.

An unavailable or invalid owner manifest keeps the authenticated socket serving panes, with a visible automatic-recovery-off reason; it is not a proof failure and never creates a pre-window stop question. An unannounced relaunch cannot reach this authority through an old disk key. Planned B3 uses the same redemption primitive with full checkpoint validation, then its independent read/write barriers, old-host exit proof and same-owner successor attach. A failed transfer keeps the exact consumed recipient pinned; explicit identity-bound consent remains available for safe retirement.

## Compatibility

An older host cannot be secured retroactively. A new main recognizes a positively identified legacy host through a bounded compatibility probe; it never sends either secret to it. Only legacy version/status reads needed to describe migration are permitted on that path, never automatic writes or handover credential claims. Live legacy panes require the existing #219 migration question before their host is stopped; Cancel keeps the old host/processes and disables unsafe pane controls with an explanation. An unknown or failing handshake alone is not evidence of a legacy host and cannot authorize replacement. Owner-backed migration may use B3 only when its required authentication and state capabilities are actually supported; otherwise it uses the confirmed fallback.

An older main cannot authenticate to the new host: it receives the fixed authentication-required refusal, no events or owner key, and cannot issue successful RPC reads/writes/kills. I will test representative prior clients. I cannot promise that arbitrary old code will show the new notice or refrain from unlinking a socket or signaling a same-UID PID outside RPC. The host must keep the native owner and children safe on rejected connections; no unauthenticated compatibility exception is added to make an older main work.

## Offline acceptance evidence

I will test absent/wrong proof, role reflection, stale/replayed nonces, another host instance, same-UID peer mismatch, unknown peer identity, pipelined RPC, slow/oversized handshake and connection-budget exhaustion. Each forbidden operation and spontaneous event path must show zero dispatch/data/side effects before authentication; an authenticated incumbent must remain usable under rejected connections. Ticket file tests cover races, symlinks, FIFO, mode/owner/link/length corruption and read failure. Migration tests prove even exact old disk keys and unsafe old key objects are ignored without reads, repair or deletion. No secret may appear in captured logs, argv, pane env, renderer messages or checkpoint files.

Real offline Electron tests will start a host, quit/relaunch main, authenticate and obtain continuity, then SIGKILL the JS host: a new JS PID must attach to the same owner and child PIDs, with unread output, input/resize and B4 hold/uncertain-write rules intact. Existing B3 handover, B4 recovery, identity-bound restart consent, busy/hold and whole e2e remain required, plus full npm tests, lint and package smoke. Sockets are disposable Unix sockets; any TCP fixture uses only 127.0.0.1 port 0. I will measure handshake/relaunch overhead and retained memory at 25 panes.

Justyna selected the memory-only boundary: clients without the held capability or a live announced ticket cannot authenticate. Ordinary configuration reads do not grant adoption, while a ticket reader during the short announcement window can race to receive authority. Process-memory inspection and a compromised authorized process remain outside this boundary; no platform identity broker is provided. B4 key continuity after ordinary relaunch requires the real announced transfer.


For the missing/wrong-key #219 fallback, I will not open unauthenticated status on a new host. Main can read the bounded private retained inventory and bind its recorded JS/owner identity to the actual socket peer. A positively identified legacy host retains only the bounded compatibility reads described above.

## Ordinary relaunch while the previous main is closing

Lead L1 separates a busy principal from a failed capability proof. After validating the client proof, the host may return a distinct busy response with its own transcript-bound HMAC; an invalid, replayed or expired proof still receives the opaque authentication failure. A live or unknown incumbent remains exclusive, and only a proven-gone process permits takeover. Startup health returns before all stop questions, including the other-host question, so the window opens with the reason "The previous Aya process is still closing." No signal, owner change, host start or socket unlink is authorized by busy.

An attach shares a ten-second acquisition budget with bounded backoff. Input remains gated through the normal replay application. The client retains its key, obtains ordinary authenticated owner continuity after takeover, and attaches to the existing panes. Expiry leaves the pane disconnected; a later explicit attach may retry. Close cancels the unsent attach even before the first busy reply, and quit cancels the wait; neither may send a late spawn. Missing/wrong capabilities retain their actual authentication-consent path.

The pre-fix comparison used one machine, one worker and shutdown=0, serially: main `8890bea3` passed all 90 cases in three full agent-session-resume repetitions (7.0 minutes); the original `e40f5a9d` build passed 84 and failed 6 (13.7 minutes), with both quit/relaunch firstWindow timeouts reproduced in every repetition and six associated teardown errors. Its earlier non-final whole run was stopped for the product fix at 94 passed, 2 failed and 375 not run (6.7 minutes); it is not final validation.
