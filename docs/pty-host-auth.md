# PTY host socket authentication - proposed design

I base this design on main `1314f7bf`, on branch `pty-host-socket-auth`. I will rebase after B4 (#230) lands. The lead provisionally approved this design for implementation on 2026-10-16; merge remains held until Justyna confirms the same-account boundary.

## Proof and its boundary

I propose a random 32-byte capability per `AYA_HOME`, stored persistently in `pty-host-auth/key` (a dedicated 0700 subdirectory). Main reads it again after an ordinary relaunch, so it can authenticate to the surviving host without an announced handover window. The file is owner-owned, mode 0600, within a checked owner-only directory; creation uses exclusive/no-follow semantics. Reads are nonblocking, regular-file-only, single-link, exact-length and permission/owner checked. Concurrent creation reads the winner; an unsafe or unreadable existing file is a refusal, never an excuse to replace a key or a running host. Development and disposable test homes have independent keys.

This proves possession of the home capability, not that the executable is Aya. Every process with the same UID can read a 0600 file, including an unsandboxed agent; root and a process able to inspect main/host memory can also obtain secrets. No code-signature or executable-path claim changes that. In particular, a same-UID reader of this capability can authenticate and request the owner credential. This is a persistent same-account trust decision, not protection against an agent already running arbitrary same-account code. If the intended boundary excludes that agent, I need a different platform identity/credential-broker design before implementation; a private file or user-wide credential store alone cannot establish that boundary.

Only main creates or explicitly replaces the capability; a host only consumes its inherited copy. Missing, unreadable or wrong capability material never authorizes silent replacement or killing of a surviving host: recovery uses the #219 question with that host's inventory, and Cancel preserves it.

The capability never enters pane environments, argv, logs, diagnostics, renderer IPC, checkpoint state or the public registry. A newly started host receives it through a dedicated inherited pipe, separate from the native-owner key and checkpoint bootstrap. The host stores it only in memory. I do not change the native owner protocol or binary and do not persist its key.

## Authenticated connection

I propose a bounded mutual HMAC-SHA256 handshake before normal JSON RPC. Client and host each contribute a fresh 32-byte nonce. Domain-separated server/client proofs cover both nonces, protocol version, host instance and kernel peer PID/start identities; proofs from another connection, role or host cannot be replayed. The main verifies the server proof before sending its client proof. Both sides require same-UID kernel peer identity, constant-time proof comparison, a small closed schema (at most 1 KiB per handshake frame) and a five-second whole-handshake deadline. Missing proof, wrong proof, malformed/oversized input or expiry closes that connection with a fixed error, without affecting live panes. Pending unauthenticated connections and their buffers have aggregate caps and do not keep an empty host alive indefinitely.

The host must not add an unauthenticated socket to its broadcast recipients, send initial spawned/snapshot/replay/exit events, or dispatch any ordinary request. Without authentication it refuses read/search/replay, write, resize, spawn/prepare, kill/shutdown, exit/display acknowledgements, composer metadata, every handover operation (including announce and claim), version and status. Only the minimal handshake/version-of-auth-protocol envelope is public; it contains no pane data, owner key or work status. Pipelined RPC cannot race authentication. Authentication errors never trigger socket unlink, host spawn, owner replacement or a legacy downgrade.

One active main principal is bound to PID plus kernel start identity; its sockets may reconnect. A different authenticated principal cannot take control while it is still live or its identity is uncertain. After the old main is proved gone, the relaunched main may become the principal. A second connection must not invalidate the first merely by sending a bad proof. All internal client paths, including health probes, handover claims and explicit restart, use the same handshake; no unprotected helper connection remains. Existing identity-bound stop consent is still required after authentication.

## Ordinary relaunch and B4 key continuity

After authentication, a new main may request a narrowly scoped in-memory owner credential response from the same host, bound to that authenticated principal and the host/owner instance. It validates the owner identity and complete bounded pane/generation/process manifest before enabling B4. No handover announcement, disk ticket or transfer window is opened for an ordinary relaunch. The native key stays only in main/host memory and the inherited pipe used for recovery. The current host and its readers continue running; authentication itself neither clears display nor respawns panes.

If credential or manifest acquisition fails, main keeps the host and panes, shows the truthful disconnected/recovery-unavailable reason when needed, and cannot enable automatic recovery. It does not substitute another owner or a new pane. Planned B3 handovers retain their checkpoint, one-use nonce and cutover barriers, with socket authentication required before announce/claim. A missing or changed capability while a host lives fails closed: no silent rotation and no destructive reset. Rotation is an explicit, separately confirmed replacement operation rather than a fallback to a failed read.

## Compatibility

An older host cannot be secured retroactively. A new main recognizes a positively identified legacy host through a bounded compatibility probe; it never sends either secret to it. Only legacy version/status reads needed to describe migration are permitted on that path, never automatic writes or handover credential claims. Live legacy panes require the existing #219 migration question before their host is stopped; Cancel keeps the old host/processes and disables unsafe pane controls with an explanation. An unknown or failing handshake alone is not evidence of a legacy host and cannot authorize replacement. Owner-backed migration may use B3 only when its required authentication and state capabilities are actually supported; otherwise it uses the confirmed fallback.

An older main cannot authenticate to the new host: it receives the fixed authentication-required refusal, no events or owner key, and cannot issue successful RPC reads/writes/kills. I will test representative prior clients. I cannot promise that arbitrary old code will show the new notice or refrain from unlinking a socket or signaling a same-UID PID outside RPC. The host must keep the native owner and children safe on rejected connections; no unauthenticated compatibility exception is added to make an older main work.

## Offline acceptance evidence

I will test absent/wrong proof, role reflection, stale/replayed nonces, another host instance, same-UID peer mismatch, unknown peer identity, pipelined RPC, slow/oversized handshake and connection-budget exhaustion. Each forbidden operation and spontaneous event path must show zero dispatch/data/side effects before authentication; an authenticated incumbent must remain usable under rejected connections. File tests cover races, symlinks, FIFO, mode/owner/link/length corruption, read failure and key mismatch without deletion or replacement. No secret may appear in captured logs, argv, pane env, renderer messages or checkpoint files.

Real offline Electron tests will start a host, quit/relaunch main, authenticate and obtain continuity, then SIGKILL the JS host: a new JS PID must attach to the same owner and child PIDs, with unread output, input/resize and B4 hold/uncertain-write rules intact. I will cover another live main, identity-unavailable takeover, repeated reconnect, stale identity, failed continuity, legacy Cancel/confirm and older-main refusal. Existing B3 handover, B4 recovery, identity-bound restart consent, busy/hold and whole e2e remain required, plus full npm tests, lint and package smoke. Sockets are disposable Unix sockets; any TCP fixture uses only 127.0.0.1 port 0. I will measure handshake/relaunch overhead and retained memory at 25 panes.

The approved boundary stops accidental and foreign clients: other `AYA_HOME` instances, stale tools and processes unable to read this home (including agents sandboxed away from it). It provides B4 key continuity after an ordinary relaunch. It does NOT stop an unsandboxed process of the same user, which can read the file. A platform identity broker is outside this PR; the lead holds merge until Justyna confirms this boundary.


For the missing/wrong-key #219 fallback, I will not open unauthenticated status on a new host. Main can read the bounded private retained inventory and bind its recorded JS/owner identity to the actual socket peer. An unavailable or unverifiable inventory is explicitly unknown, never an empty-pane assertion; the host stays alive on Cancel. A positively identified legacy host retains only the bounded compatibility reads described above.
