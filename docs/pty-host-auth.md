# PTY host socket authentication - proposed design

I base this design on main `8890bea3` (merged B4), on branch `pty-host-socket-auth`. The authentication work has been rebased onto merged B4 (#230). The lead provisionally approved this design for implementation on 2026-10-16; merge remains held until Justyna confirms the same-account boundary.

## Proof and its boundary

I propose a random 32-byte capability per `AYA_HOME`, stored persistently in `pty-host-auth/key` (a dedicated 0700 subdirectory). Main reads it again after an ordinary relaunch, so it can authenticate to the surviving host without an announced handover window. The file is owner-owned, mode 0600, within a checked owner-only directory; creation uses exclusive/no-follow semantics. Reads are nonblocking, regular-file-only, single-link, exact-length and permission/owner checked. Concurrent creation reads an already completed winner; an in-progress or crashed writer with an incomplete file is refused without repair, and a later explicit read may succeed after completion; an unsafe or unreadable existing file is a refusal, never an excuse to replace a key or a running host. Development and disposable test homes have independent keys.

This proves possession of the home capability, not that the executable is Aya. Every process with the same UID can read a 0600 file, including an unsandboxed agent; root and a process able to inspect main/host memory can also obtain secrets. No code-signature or executable-path claim changes that. In particular, a same-UID reader of this capability can authenticate and request the owner credential. This is a persistent same-account trust decision, not protection against an agent already running arbitrary same-account code. If the intended boundary excludes that agent, I need a different platform identity/credential-broker design before implementation; a private file or user-wide credential store alone cannot establish that boundary.

Only main creates or explicitly replaces the capability; a host only consumes its inherited copy. Missing, unreadable or wrong capability material never authorizes silent replacement or killing of a surviving host: recovery uses the #219 question with that host's inventory, and Cancel preserves it.

The capability never enters pane environments, argv, logs, diagnostics, renderer IPC, checkpoint state or the public registry. A newly started host receives it through a dedicated inherited pipe, separate from the native-owner key and checkpoint bootstrap. The host stores it only in memory. I do not change the native owner protocol or binary and do not persist its key.

## Authenticated connection

I propose a bounded mutual HMAC-SHA256 handshake before normal JSON RPC. Client and host each contribute a fresh 32-byte nonce. Domain-separated server/client proofs cover both nonces, protocol version, host instance and kernel peer PID/start identities; proofs from another connection, role or host cannot be replayed. The main verifies the server proof before sending its client proof. Both sides require same-UID kernel peer identity, constant-time proof comparison, a small closed schema (at most 1 KiB per handshake frame) and a five-second whole-handshake deadline. Missing proof, wrong proof, malformed/oversized input or expiry closes that connection with a fixed error, without affecting live panes. Pending unauthenticated connections and their buffers have aggregate caps and do not keep an empty host alive indefinitely.

The host must not add an unauthenticated socket to its broadcast recipients, send initial spawned/snapshot/replay/exit events, or dispatch any ordinary request. Without authentication it refuses read/search/replay, write, resize, spawn/prepare, kill/shutdown, exit/display acknowledgements, composer metadata, every handover operation (including announce and claim), version and status. Only the minimal handshake/version-of-auth-protocol envelope is public; it contains no pane data, owner key or work status. Pipelined RPC cannot race authentication. Authentication errors never trigger socket unlink, host spawn, owner replacement or a legacy downgrade.

One active main principal is bound to PID plus kernel start identity; its sockets may reconnect. A different authenticated principal cannot take control while it is still live or its identity is uncertain. After the old main is proved gone, the relaunched main may become the principal. A second connection must not invalidate the first merely by sending a bad proof. All internal RPC paths, including handover claims and explicit restart, use the same handshake; no unprotected status helper remains. Socket discovery may read only the kernel peer identity without sending an RPC or either credential. Existing identity-bound stop consent is still required after authentication.

## Ordinary relaunch and B4 key continuity

After authentication, a new main may request a narrowly scoped in-memory owner credential response from the same host, bound to that authenticated principal and the host/owner instance. It validates the owner identity and complete bounded pane/generation/process manifest before enabling B4. No handover announcement, disk ticket or transfer window is opened for an ordinary relaunch. The native key stays only in main/host memory and the inherited pipe used for recovery. The current host and its readers continue running; authentication itself neither clears display nor respawns panes.

If credential or manifest acquisition fails, main keeps the host and panes, shows the truthful disconnected/recovery-unavailable reason when needed, and cannot enable automatic recovery. It does not substitute another owner or a new pane. Planned B3 handovers retain their checkpoint, one-use nonce and cutover barriers, with socket authentication required before announce/claim. A missing or changed capability while a host lives fails closed: no silent rotation and no destructive reset. Rotation is an explicit, separately confirmed replacement operation rather than a fallback to a failed read.

## Compatibility

An older host cannot be secured retroactively. A new main recognizes a positively identified legacy host through a bounded compatibility probe; it never sends either secret to it. Only legacy version/status reads needed to describe migration are permitted on that path, never automatic writes or handover credential claims. Live legacy panes require the existing #219 migration question before their host is stopped; Cancel keeps the old host/processes and disables unsafe pane controls with an explanation. An unknown or failing handshake alone is not evidence of a legacy host and cannot authorize replacement. Owner-backed migration may use B3 only when its required authentication and state capabilities are actually supported; otherwise it uses the confirmed fallback.

An older main cannot authenticate to the new host: it receives the fixed authentication-required refusal, no events or owner key, and cannot issue successful RPC reads/writes/kills. I will test representative prior clients. I cannot promise that arbitrary old code will show the new notice or refrain from unlinking a socket or signaling a same-UID PID outside RPC. The host must keep the native owner and children safe on rejected connections; no unauthenticated compatibility exception is added to make an older main work.

## Offline acceptance evidence

I will test absent/wrong proof, role reflection, stale/replayed nonces, another host instance, same-UID peer mismatch, unknown peer identity, pipelined RPC, slow/oversized handshake and connection-budget exhaustion. Each forbidden operation and spontaneous event path must show zero dispatch/data/side effects before authentication; an authenticated incumbent must remain usable under rejected connections. File tests cover races, symlinks, FIFO, mode/owner/link/length corruption, read failure and key mismatch without deletion or replacement. No secret may appear in captured logs, argv, pane env, renderer messages or checkpoint files.

Real offline Electron tests will start a host, quit/relaunch main, authenticate and obtain continuity, then SIGKILL the JS host: a new JS PID must attach to the same owner and child PIDs, with unread output, input/resize and B4 hold/uncertain-write rules intact. I will cover another live main, identity-unavailable takeover, repeated reconnect, stale identity, failed continuity, legacy Cancel/confirm and older-main refusal. Existing B3 handover, B4 recovery, identity-bound restart consent, busy/hold and whole e2e remain required, plus full npm tests, lint and package smoke. Sockets are disposable Unix sockets; any TCP fixture uses only 127.0.0.1 port 0. I will measure handshake/relaunch overhead and retained memory at 25 panes.

The approved boundary stops accidental and foreign clients: other `AYA_HOME` instances, stale tools and processes unable to read this home (including agents sandboxed away from it). It provides B4 key continuity after an ordinary relaunch. It does NOT stop an unsandboxed process of the same user, which can read the file. A platform identity broker is outside this PR; the lead holds merge until Justyna confirms this boundary.


For the missing/wrong-key #219 fallback, I will not open unauthenticated status on a new host. Main can read the bounded private retained inventory and bind its recorded JS/owner identity to the actual socket peer. An unavailable or unverifiable inventory is explicitly unknown, never an empty-pane assertion; the host stays alive on Cancel. A positively identified legacy host retains only the bounded compatibility reads described above.

## Scoped implementation evidence

Stage 1 (`31b0ba6b`) is an unused main-only file helper and pure handshake. It passes 17 contracts in Node 26 and Electron 43.5/Node 24.19; the reviewer independently reran both and mutation-checked the host-instance proof and valid-ready deadline refusals. Auth findings F1-F3 are fixed. No socket dispatch was changed at that stage.

Stage 2 adds an unused Unix-stream gate: at most 32 pending handshakes, one five-second deadline, fixed refusals and a paused stream on success so normal parsing can take ownership without losing bytes. A different authenticated main cannot displace a live or unverifiable incumbent. Nine contracts pass in both runtimes, including a real separate process authenticated through kernel socket credentials, pre-auth and pipelined RPC refusal, wrong capability, failed peer lookup, oversized input, silent timeout, connection budget and incumbent continuity. Socket/host/main integration and ordinary-relaunch key continuity remain the next stage; these results do not claim that the product socket is already protected.

Stage 3 wires the host's recipient set, initial replay and entire request parser behind authentication, and main passes the capability through inherited descriptor 5. The bootstrap accepts exactly 32 pipe bytes with a cancellable five-second deadline and never reads the persistent file. The client's create-host fallback accepts only absent/refused sockets and refuses a recorded live host; authentication/key failures cannot enter it. Real-host tests exercise every declared request plus unknown names before proof, a pending client's exclusion from live output, and missing/unsafe/wrong keys preserving host/pane PIDs and the socket inode with zero start attempts. Bootstrap tests cover missing, malformed, regular-file and never-closed inheritance. Existing spawn, input/search/exit and preparation cancellation tests pass. The exact core import graph includes authentication/bootstrap but excludes the main-only key-file helper. Legacy/UI consent fallback, authenticated health discovery, ordinary-relaunch owner-key continuity and launcher compatibility remain integration work, not completed claims.


After the B4 rebase, the 53 auth/bootstrap/core-graph/spawn-preparation contracts pass in both runtimes. Auth F4 replaces diagnostic-list emptiness with a main-only three-state start proof. A verified live record or any unknown registry/probe state blocks creation, including owner-record reader metadata when no group-leading host record exists. Only verified gone/reused records allow it. The check runs before capability creation and again immediately before socket unlink/fork. Seven new contracts pin both ENOENT and ECONNREFUSED paths, a previously verified PID followed by ps EAGAIN, registry read failure, malformed/private/incomplete records, safe gone allowance and zero unlink/fork on final refusal. The combined set passes 60/60 in Node and Electron. The #219 UI for an unknown/refused inventory is still the next integration stage; refusal does not silently start a host.

The lead approved a verified individual SIGTERM for the confirmed fallback: a yes is bound to the exact host, never a group, and a changed/unverifiable target requires a fresh question before any signal. The bridge reuses the existing Linux pidfd/two-identity-check path; macOS retains the documented immediate-check residual PID-reuse window. No owner protocol or executable change is needed. Rebuilding before/after the bridge change leaves the unsigned owner SHA256 identical: `2d93372d8249dd1c3a7593d0869f863fdb53971c36076c71dad9939a5a3e4109`. Native race fixtures now exercise both SIGKILL and SIGTERM, including disappearance and PID reuse between checks, and reject unsupported signals before any probe. A real child accepts only its matching identity, handles SIGTERM and exits 23 in both runtimes. The bridge API is not yet connected to a restart action; the coordinator must still log the checked identity and prove the A-to-B question race.


The verified SIGTERM contract also runs in the native owner matrix; Linux requires successful pidfd signaling (`AYA_OWNER_EXPECT_PIDFD=1`), while unsupported local emulation may refuse safely. Auth F5 is fixed in `cef51983`; actual native Linux success remains an external CI gate.

The next unused main-only status helper reads retained owner metadata only after binding its recorded JS PID/start time to the socket peer's kernel instance. It preserves pane PIDs and uncertain spawn intents without opening an owner connection, requesting a key, signaling or spawning. Missing, unsafe, changed or unverifiable records explicitly set inventory unknown; they cannot become a verified empty inventory. Legacy private host records can verify a target but cannot invent its pane list. Owner-record reads are bounded at 64 KiB and open nonblocking/no-follow before checking file type, so a FIFO is refused promptly. Six new contracts cover the retained process list, reader/kernel mismatch, late probe failure, legacy unknown inventory, unsafe files and FIFO refusal. This helper is not yet wired into status or a destructive action.


Status integration now captures the kernel peer before attempting to read the capability, so missing/unsafe/wrong keys retain the same bound private process list. Diagnostics carries explicit authentication/unknown-inventory warnings instead of describing failed authentication as a code-version mismatch. Socket discovery sends no bytes and reads only kernel peer identity; even a silent or misleading server cannot supply a fabricated PID through an unprotected version reply. The status/integration/health/core-graph set passes 33/33 in both runtimes. Restart signaling, initial pane refusal presentation, legacy migration and ordinary-relaunch owner-key continuity remain subsequent work; this stage does not permit stopping an unauthenticated host.


The restart coordinator now handles a confirmed authentication failure separately from authenticated shutdown. Launch and Diagnostics ask explicitly, even when no busy screen or verified pane inventory is available; known pane names/PIDs are listed and unknown inventory is called unknown. Consent is bound to PID, kernel start identity and owner instance. The coordinator reopens the socket for kernel-peer/private-ledger inspection after the asynchronous question and again after the group probe, then sends only the verified individual SIGTERM and logs its checked identity/outcome. Changed/unverifiable targets require a new question; native mismatch/unknown never retries or escalates. Quit cancels before signaling. A signalled host gets five seconds to exit, with no force-kill or implicit successor in this fallback. An authentication refusal without explicit target consent throws instead of reporting a successful restart. The existing suspend/resume logic preserves B4's spent recovery budget on refusal.

Forty coordinator/health/consent contracts pass in Node and Electron, including a real host with its capability removed: status retains the child PID, unconsented restart refuses, exact consent delivers one host SIGTERM, the old host shuts down its owner and pane, and no successor is spawned. Deterministic A-to-B fixtures cover both the first inspection and the final pre-signal inspection; Cancel sends no signal, and fresh consent is revalidated. The real fallback contract joins the native matrix so Linux requires pidfd signaling. This is scoped backend coverage, not final GUI/legacy/ordinary-relaunch continuity completion.


Initial attachment refusal now emits a disconnected event with a plain authentication/inventory reason and preserves it for later window sinks. The rejected spawn uses the renderer's existing handled-disconnection message while retaining its typed error code; it never emits no-session or exit for an unverified live pane. A confirmed fallback restart clears those notices only after the old host is proved gone. The real missing/unsafe/wrong-key contracts check the reason, friendly rejection, late-sink hydration, unchanged processes and zero starts (10/10 integration/status contracts in each runtime). Actual-window coverage remains part of the final GUI stage.
