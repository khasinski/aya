# Local user screen rules - PR2 design

I propose this PR on main `ead520c8`, after rules PR1 (#232). This is a design note, not implementation. Socket authentication (#231) remains a separate branch; I will rebase when it lands. Remote rules, downloads and authority to distribute approval rules remain PR3 and require Justyna's decision. The startup process sweep becoming asynchronous is also a separate item.

## Files and precedence

I propose an optional private `AYA_HOME/screen-rules/` directory, with at most six recognized files: `generic.json`, `claude.json`, `codex.json`, `opencode.json`, `grok.json` and `antigravity.json`. An absent directory or an intentionally absent agent file uses the reviewed built-ins. There is no recursive discovery, arbitrary import or executable extension. Unknown `.json` names are a configuration error; editor temporary files are ignored. Reading state does not create the directory.

Each file has the closed envelope `{schemaVersion: 1, ruleSetVersion: "local-1", agent: "claude", rules: [...]}`. The agent must match its filename. Rule records use PR1's exact `{id, kind, region, pattern, flags}` fields and enumerations. Regions and agent selection stay the same: preset kind, never process name; hooks remain opt-in. Pattern strings are data, not code. There is no script, replacement expression, `eval`, external reference or remote source.

For each kind, matching order is agent-specific user file, generic user file, then the existing built-in order. An authored array keeps its order. The existing priority between kinds remains dialog, suppressor, prompt; busy, usage-limit and account-setting keep their current independent policy positions. A user prompt therefore does not bypass a matching built-in dialog. A matching user rule is the winning evidence. I propose allowing an existing built-in ID as an explicit replacement: the highest-priority user definition masks that ID's built-in definition, and explain records its user source. Duplicate user IDs across files are rejected rather than silently choosing one. There is no separate disable/include mechanism in this PR. Empty user files add no rules.

The effective version combines the built-in version/digest with ordered file versions/content digests and the precedence format version. File basenames, versions and IDs remain bounded labels. Explain names sources as `user/claude.json` or `user/generic.json`, never arbitrary full paths, and retains PR1's control/bidi/escape stripping, one-field pane-name quoting and excerpt cap. No-match, code-only policy, unknown-screen and shell answers keep their existing meanings.

## Real validation and the runtime boundary

I retain PR1's closed schema, strict UTF-8 and duplicate-key checks, allowed non-stateful `i/m/u` flags, depth/token bounds, 80-character ASCII IDs, 2048-character pattern cap and 64 KiB-plus-one bounded reads. The six files total at most 384 KiB. I propose a combined 256 authored-rule cap including built-ins and at most 128 effective rules per agent after inheritance and replacement. Directory and files must belong to the current user, with directory mode 0700 and file mode 0600, regular single-link files only; symlinks, FIFOs, devices, oversized/changing files and unsafe directory replacements are refused using nonblocking/no-follow opens and inode/metadata rechecks. No watcher reads a growing file without the cap.

The complexity checker remains test-only lint and is never an admission guarantee. Main validates raw structure and metadata without constructing a RegExp for any non-built-in pattern. Compilation, syntax validation and every evaluation of user patterns happen in an isolated Node worker thread. Even a user pattern byte-identical to a built-in follows that worker path. No fallback executes it on main, in a renderer or in the PTY host.

I propose one worker per main, one evaluation in flight, a 100 ms hard active-evaluation deadline and a separate 2 s worker initialization deadline. Main terminates the worker on overrun, worker error or malformed response; an unavailable effective set gives agent hold unknown, busy false, no clear waiting edge and explicit `rules unavailable` in explain. It never falls back silently to built-ins while an invalid user configuration is present. Shell hold remains shell, and B4's unknown-screen proof stays authoritative. The failed digest remains quarantined until a file-content change; state polling cannot restart an offending worker indefinitely. A worker termination is awaited before replacing it, and quit cancels startup/evaluation/reload.

Main bounds queued work: at most one latest snapshot per pane, 25 pane entries, a 16 MiB aggregate queued text budget, and a 4 MiB per-request UTF-8 region-text budget. A queued request has an absolute 1 s end-to-end deadline including waiting; exceeding a bound produces an explicit unknown result, never truncated detection text or a stale clear verdict. Requests carry only needed region text and rule-set identity, not commands, environment or replay history. Worker heap/stack limits start at 64 MiB/4 MiB. These proposed budgets need measurement on recorded screens and 25 panes before I claim they meet latency/memory requirements; a necessary change returns to lead before implementation depends on it.

## Main policy and fresh-state coordination

No-user-file installations retain the existing reviewed built-in fast path and equivalence tests. With user rules, a main-owned asynchronous coordinator requests bounded match evidence for the effective rules, then applies startup/draft/composer/recovery/shell and numbered-choice policy in main. The worker does not mutate composerSeen, acknowledge native exits or send terminal input. Main checks returned rule IDs/kinds/regions/positions against the active manifest and derives/sanitizes excerpts from its own snapshot.

One evaluation supplies busy, hold, waiting/dialog and explain together. Its key includes rule epoch/digest, pane generation and the applied snapshot revision; pasted-draft exclusion is part of the request where required. Snapshot changes, pane reuse, close or reload invalidate pending results. A delayed clear result may never mark a newer screen/composerSeen as applied. Team delivery and restart await the same fresh evaluation, while VT status fanout schedules it and ignores stale completions. Until current evaluation completes, hold is unknown and busy fails open. `aya pane state` remains read-only and uses the authenticated existing-host snapshot path; missing/refused sockets still cannot create a host, owner or key.

I will factor the existing synchronous policy into pure decision functions supplied with one match-evidence result, retaining its old built-in entry points for parity tests. This avoids a second policy implementation in the worker. All main consumers must use the coordinator when user rules are configured; no overlooked synchronous consumer may apply user patterns or release a hold from an old built-in result. The host continues owning PTY/VT only, so neither worker/rules data nor policy enter its import graph or content hash. Local rule reload never replaces the JS host or native owner and never changes pane PIDs.

## Reload and visible failure

Main watches the directory and also performs a bounded periodic metadata scan (proposed 1 s) because watch events can be lost. It coalesces editor bursts for 100 ms. On noticing a change, it invalidates the epoch immediately and keeps hold unknown until a stable bounded read, worker validation and fresh evaluation complete. A candidate is activated as a whole; no partial multi-file set or per-pane mixed epoch is published. Deletion becomes an intentional built-in fallback only after a stable rescan, so an atomic rename's brief gap cannot clear a hold. Late worker replies from the prior epoch are discarded.

Invalid files, regex syntax, timeout, resource/queue limits and worker death each log one sanitized diagnostic per digest/reason and are visible in explain as `rules unavailable` with a short reason and safe source label. A reload-failed state also appears in Diagnostics; normal VT status must not emit a false clear edge. Correcting/removing the file recovers without restarting the host; the next current snapshot is evaluated before delivery resumes. No secrets, raw screen or regex-controlled strings go to diagnostics. The user owns these local rules and can change approval detection; this is not a sandbox against unsandboxed code running as that user.

## Done criteria and evidence

- Loader tests pin exact limits, closed fields/duplicate keys, six-file aggregation, directory/file races, symlink/FIFO refusal, bounded growing reads, deterministic precedence, built-in ID replacement and source/version/digest changes. Missing directory changes nothing.
- Worker tests execute known pathological patterns (including finite ambiguous repetitions and Unicode-folding cases), assert the hard timeout and actual worker termination, and prove main's independent heartbeat/input remains responsive. A main RegExp-construction spy rejects any user source that reaches main. Invalid/overrun sets fail closed without a respawn loop; correcting the digest recovers.
- Recorded-session equivalence covers every built-in agent with no overrides, then controlled user overrides with expected hold/busy/dialog/explain evidence. Generation/snapshot/epoch races, pasted drafts, pending reload, backpressure and timeout tests reject stale clear results and preserve B3/B4 screen/composer contracts.
- Actual GUI/CLI tests create/edit/delete local rules while busy and held panes keep their owner/child PIDs; explain changes source/version, a prompt blocks delivery, a corrected rule releases it only after current evaluation, and a catastrophic pattern gives unknown hold while another pane accepts input. Reload and missing-host state commands must not start/unlink hosts. Auth busy/refusal and ordinary relaunch keep their covered behavior.
- Run npm tests, lint, Node/Electron contracts, staged package worker/data smoke, affected and whole offline GUI (shutdown=0, workers=1, default ceiling). Test real packaged worker loading from ASAR and no network or production files. Measure cold worker start, p50/p95/max evaluation and reload latency, worst timeout/termination delay, main-loop delay/CPU and main+worker memory on 25 active/idle recorded panes, with raw samples and scope retained.

The important risks are asynchronous integration accidentally trusting an old clear verdict, reload ambiguity, and worker/IPC budgets becoming visible latency. Those are acceptance gates, not reasons to weaken fail-closed hold. There is no product implementation in this commit. I am asking lead to approve the file/precedence/replacement choices and proposed budgets before code.
