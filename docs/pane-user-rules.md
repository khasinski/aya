# Local user screen rules - PR2 design

I propose this PR on main `ead520c8`, after rules PR1 (#232). The accepted design below is being implemented in separately reviewed stages; the first stage adds unused protocol/host primitives, not user-file evaluation or delivery integration. Socket authentication (#231) remains a separate branch; I will rebase when it lands. Justyna deferred PR3: no remote rules, downloads or remote approval-rule authority are included; step3 ends with PR2. The startup process sweep becoming asynchronous is also a separate item.

## Files and precedence

I propose an optional private `AYA_HOME/screen-rules/` directory, with at most six recognized files: `generic.json`, `claude.json`, `codex.json`, `opencode.json`, `grok.json` and `antigravity.json`. An absent directory or an intentionally absent agent file uses the reviewed built-ins. There is no recursive discovery, arbitrary import or executable extension. Unknown `.json` names are a configuration error; editor temporary files are ignored. Reading state does not create the directory.

Each file has the closed envelope `{schemaVersion: 1, ruleSetVersion: "local-1", agent: "claude", rules: [...]}`. The agent must match its filename. Rule records use PR1's exact `{id, kind, region, pattern, flags}` fields and enumerations. Regions and agent selection stay the same: preset kind, never process name; hooks remain opt-in. Pattern strings are data, not code. There is no script, replacement expression, `eval`, external reference or remote source.

The lead decision is additive rules only. Built-ins always apply and cannot be replaced, disabled or suppressed by user files. Any user ID colliding with any built-in ID is refused; duplicate user IDs across files are refused too. An authored array keeps its order; among user matches of the same kind, agent-specific file precedes generic. Users may add prompt, dialog, busy, usage-limit and account-setting rules. A user suppressor can suppress only user-added prompts, never a built-in prompt/dialog/hold. Built-in suppressors retain their existing scope. The existing built-in dialog/suppressor/prompt ordering and policy remain unchanged.

Main evaluates the built-in verdict independently and adds user evidence: waiting/dialog/hold and busy can be added, never removed. If both sources hold, explain retains the built-in reason and also identifies the user rule that adds a hold. A clear user verdict cannot cancel a built-in verdict. Fixing a wrong built-in requires a code change or PR3's separately authorized channel. The reason for this boundary is that anything able to write AYA_HOME, including an agent, must not be able to turn off its own built-in approval detection and let team delivery approve it.

Composition carries input protection separately from the display reason. A decision has its hold, contributing evidence and `blocksAutomatedInput`; a user-only account dialog wins that protection even if another builtin hold supplies additional provenance. Existing `HOLD_ACCOUNT_SETTING` protection remains unchanged; a user account dialog gets a generic user-only reason, not Claude-specific account text. Both the control pre-paste and pre-Enter guards consume that protection, rather than inferring it only from the old single hold string. Unknown/pending user safety also refuses automated input; interactive user input remains the user's. Builtin startup/draft/recovery cannot hide a proven account-dialog protection, and untrusted stale/unknown screens cannot prove that protection absent.

| Builtin evidence | User evidence | Effective decision |
| --- | --- | --- |
| Prompt/dialog | Clear or user suppressor | Builtin waiting/hold retained; user suppressor cannot clear it |
| No dialog/hold | User prompt or dialog | Added approval hold/wait; user prompt alone may be cleared by a user suppressor, user dialog may not |
| Any ordinary hold, or none | Active builtin/user dialog or numbered choice plus user account match | User-only protection wins; retain builtin provenance separately; direct pane-send refused before paste and before Enter |
| Any builtin user-only dialog | Any user result | Builtin user-only protection retained |
| Any ordinary hold, or none | Active dialog/choice plus user usage-limit match | Add usage-limit hold, retaining stronger user-only protection if present |
| No active prompt/dialog/choice | User account/usage text alone | No account/usage hold from transcript text; existing builtin startup/draft/other holds still apply |
| Any builtin state | User busy match | Busy is the OR of builtin and user busy, never replaced by user clear |
| Any builtin state | Unavailable/pending user layer | Keep builtin verdicts; add unknown where user safety is unresolved; never a clear edge or automated input authorization |

Tests cover this matrix through both normal hold and real control delivery, including an account dialog appearing after paste but before Enter, and standalone account/usage transcript text with no active dialog.

The effective version combines the built-in version/digest with ordered file versions/content digests and the precedence format version. File basenames, versions and IDs remain bounded labels. Explain names sources as `user/claude.json` or `user/generic.json`, never arbitrary full paths, and retains PR1's control/bidi/escape stripping, one-field pane-name quoting and excerpt cap. No-match, code-only policy, unknown-screen and shell answers keep their existing meanings.

## Real validation and the runtime boundary

I retain PR1's closed schema, strict UTF-8 and duplicate-key checks, allowed non-stateful `i/m/u` flags, depth/token bounds, 80-character ASCII IDs, 2048-character pattern cap and 64 KiB-plus-one bounded reads. The six files total at most 384 KiB. I propose a combined 256 authored-rule cap including built-ins and at most 128 effective rules per agent after inheritance. Directory and files must belong to the current user, with directory mode 0700 and file mode 0600, regular single-link files only; nonblocking/no-follow opens refuse unsafe entry types, and every file read is bounded. File metadata and before/after directory device/inode rechecks are accident guards. The directory is trusted as the user's own: these checks do not prove path identity against a same-UID writer or ancestor/path ABA, and such a writer can already edit the additive rules directly. A path swap never bypasses the same private-file/type/size checks on the resulting rule file. No watcher reads a growing file without the cap.

The complexity checker remains test-only lint and is never an admission guarantee. Main validates raw structure and metadata without constructing a RegExp for any non-built-in pattern. Compilation, syntax validation and every evaluation of user patterns happen in an isolated Node worker thread. Even a user pattern byte-identical to a built-in follows that worker path. No fallback executes it on main, in a renderer or in the PTY host.

I propose one worker per main, one evaluation in flight, a 100 ms hard active-evaluation deadline and a separate 2 s worker initialization deadline. Every reload candidate gets a fresh worker; its initialization deadline includes all compilation and validation, with no unbounded compile message to a running worker. Main owns monotonic absolute deadlines from initialization dispatch, request queue entry and evaluation dispatch. It checks elapsed time again before accepting even a valid reply: a reply at/after its deadline is refused even if the timer callback has not run. Worker "started" messages never reset a parent deadline.

Main terminates the worker on active execution/compilation overrun, worker error or malformed response; an unavailable user set preserves all built-in decisions and adds a visible user-rules-unavailable diagnostic. Where built-ins do not already hold, the unavailable additive layer keeps hold unknown; its busy contribution fails open to false, never removing built-in busy. It cannot emit a clear waiting edge over a built-in wait or an unresolved user layer. Explain distinguishes built-in evidence from unavailable user rules. This is conservative fallback, not silently ignoring a user configuration. Shell hold remains shell, and B4's unknown-screen proof stays authoritative. An execution/compilation-failed digest remains quarantined until a file-content change; state polling cannot restart an offending worker indefinitely. Transient queue/backpressure expiry instead invalidates only that request, keeps current safety unknown and allows a later bounded request to recover without editing valid files. A worker termination is awaited before replacing it, and quit cancels startup/evaluation/reload.

Main bounds queued work: at most one latest request per identical pane/revision/caller/exclusion context, 25 queued contexts (therefore at most25 queued panes), a 16 MiB aggregate queued text budget, and a 4 MiB per-request UTF-8 region-text budget. A queued request has an absolute 1 s end-to-end deadline including waiting; exceeding a bound produces an explicit unknown result, never truncated detection text or a stale clear verdict. Requests carry only needed region text and rule-set identity, not commands, environment or replay history. The worker starts with V8 old-generation/JS-stack limits of64MiB/4MiB; these are not an OS RSS ceiling. These proposed budgets need measurement on recorded screens and 25 panes before I claim they meet latency/memory requirements; a necessary change returns to lead before implementation depends on it.

## Main policy and fresh-state coordination

No-user-file installations start no worker at all and retain the existing reviewed built-in fast path and equivalence tests. I will measure zero worker/IPC overhead there and the added latency separately with user files present. With user rules, a main-owned asynchronous coordinator requests bounded match evidence for user rules, then applies startup/draft/composer/recovery/shell and numbered-choice policy in main. The worker does not mutate composerSeen, acknowledge native exits or send terminal input. Main checks returned rule IDs/kinds/regions/positions against the active manifest and derives/sanitizes excerpts from its own snapshot.

One evaluation supplies busy, hold, waiting/dialog and explain together. Its key includes rule epoch/digest, pane generation and the applied snapshot revision; pasted-draft exclusion is part of the request where required. Snapshot changes, pane reuse, close or reload invalidate pending results. A delayed clear result may never mark a newer screen/composerSeen as applied. Team delivery and restart await the same fresh evaluation, while VT status fanout schedules it and ignores stale completions. Until current user evaluation completes, built-ins continue to apply, hold cannot clear from pending user evidence, and only the user busy contribution fails open. `aya pane state` remains read-only and uses the authenticated existing-host snapshot path; missing/refused sockets still cannot create a host, owner or key.

Generation alone is insufficient. I propose a host-issued monotonic state revision included in each applied snapshot, advanced for incoming/applied output, relevant resize, recovery-screen and composerSeen changes. A snapshot is exportable only after its pending parser work is applied; receiving new bytes invalidates an earlier decision immediately, before its debounced broadcast. Main revalidates generation/revision with the host before applying an asynchronous result, and composerSeen ACK carries the exact generation/revision and is refused on mismatch or pending parser work. Cache/coalescing keys also include consumer purpose/caller scope and the digest of the exact pasted exclusion; a read-only explain consumer never borrows an ACK side effect from a delivery consumer.

For delivery, a positive check is not a permanent authorization: pre-paste and pre-Enter are distinct fresh decisions, and guarded automatic writes carry the checked generation/revision so the host atomically refuses a changed state before accepting input. This closes the applied-but-not-yet-broadcast output window instead of trusting only main's most recently received event. A refusal sends nothing and requires a fresh decision within the existing delivery budget; uncertain writes are never retried. This adds only protocol/VT metadata and conditional-input checks to the host, no screen rules. It changes JS-host bytes once for this feature, so existing B3 replacement/#219 migration policy applies; subsequent rule-file edits still do not change the host content hash or native owner.

Regressions must apply new output in the same host generation without broadcasting it, then complete the old worker request: the old result, composer ACK and conditional input must be refused. Resize/recovery/composer mutations and two concurrent distinct pasted exclusions get equivalent coverage. Old hosts lacking revision support cannot enable user-rule automated delivery; built-ins remain available with explicit unknown user safety until normal consented migration, never a silent host restart.

I will factor the existing synchronous policy into pure decision functions supplied with one match-evidence result, retaining its old built-in entry points for parity tests. This avoids a second policy implementation in the worker. All main consumers must use the coordinator when user rules are configured; no overlooked synchronous consumer may apply user patterns or release a hold from an old built-in result. The host continues owning PTY/VT only, so neither worker/rules data nor policy enter its import graph or content hash. Local rule reload never replaces the JS host or native owner and never changes pane PIDs.

## Reload and visible failure

Main watches the directory and also performs a bounded periodic metadata scan (proposed 1 s) because watch events can be lost. It coalesces editor bursts for 100 ms. On noticing a change, it invalidates the epoch immediately and keeps hold unknown until a stable bounded read, worker validation and fresh evaluation complete; built-in verdicts remain authoritative throughout. A candidate is activated as a whole; no partial multi-file set or per-pane mixed epoch is published. Deletion becomes an intentional built-in fallback only after a stable rescan, so an atomic rename's brief gap cannot clear a hold. Late worker replies from the prior epoch are discarded.

Invalid files, regex syntax, timeout, resource/queue limits and worker death each log one sanitized diagnostic per digest/reason and are visible in explain as `rules unavailable` with a short reason and safe source label. A reload-failed state also appears in Diagnostics; normal VT status must not emit a false clear edge. Correcting/removing the file recovers without restarting the host; the next current snapshot is evaluated before delivery resumes. No secrets, raw screen or regex-controlled strings go to diagnostics. The user owns these local rules and can change approval detection; this is not a sandbox against unsandboxed code running as that user.

## Done criteria and evidence

- Loader tests pin exact limits, closed fields/duplicate keys, six-file aggregation, directory/file races, symlink/FIFO refusal, bounded growing reads, deterministic precedence, built-in ID collision refusal and additive-only composition and source/version/digest changes. Missing directory changes nothing.
- Worker tests execute known pathological patterns (including finite ambiguous repetitions and Unicode-folding cases), assert the hard timeout and actual worker termination, and prove main's independent heartbeat/input remains responsive. A main RegExp-construction spy rejects any user source that reaches main. Invalid/overrun user sets retain built-in holds/busy, add unknown hold where necessary and never enter a respawn loop; correcting the digest recovers.
- Deadline tests stall compilation during reload, terminate the candidate and preserve builtin safety; a valid response delivered after a monotonic deadline but before a delayed timer callback cannot clear. A queue expiry recovers on a later request without changing the digest.
- Recorded-session equivalence covers every built-in agent with no overrides, then controlled additive user rules with expected hold/busy/dialog/explain evidence. A user suppressor, colliding ID, failed worker or reload must never clear a built-in approval/usage/account/startup/recovery hold. Generation/snapshot/epoch races, pasted drafts, pending reload, backpressure and timeout tests reject stale clear results and preserve B3/B4 screen/composer contracts.
- Actual GUI/CLI tests create/edit/delete local rules while busy and held panes keep their owner/child PIDs; explain changes source/version, a prompt blocks delivery, a corrected rule releases it only after current evaluation, and a catastrophic pattern gives unknown hold while another pane accepts input. Reload and missing-host state commands must not start/unlink hosts. Auth busy/refusal and ordinary relaunch keep their covered behavior.
- Run npm tests, lint, Node/Electron contracts, staged package worker/data smoke, affected and whole offline GUI (shutdown=0, workers=1, default ceiling). Test real packaged worker loading from ASAR and no network or production files. Measure cold worker start, p50/p95/max evaluation and reload latency, worst timeout/termination delay, main-loop delay/CPU and main+worker memory on 25 active/idle recorded panes, with raw samples and scope retained.

The important risks are asynchronous integration accidentally trusting an old clear verdict, reload ambiguity, and worker/IPC budgets becoming visible latency. Those are acceptance gates, not reasons to weaken fail-closed hold. The lead approved the six-file format, additive-only composition, worker budgets and atomic reload on 2026-10-16. No user files means no worker. This note incorporates that decision; product implementation follows separately. The conservative unavailable-user composition above preserves built-in decisions and adds unknown hold where needed, rather than allowing a failed user worker to clear a hold.

## Stage 1 - host revisions and conditional input

I added an opaque applied revision to snapshots: a fresh per-mirror epoch plus a non-reused counter. Incoming output invalidates the previous revision before parsing or debounced fanout; a usable revision is absent until every pending write callback has applied. Resize, composer acknowledgement and recovery-state changes invalidate it too. A planned restore preserves generation but creates a fresh revision epoch. Existing generation-only consumers retain their behavior until the coordinator stage.

The separate `snapshot-check`, `composer-seen-checked` and `write-fenced` verbs require a closed generation/revision identity. An older host cannot ignore an optional fence and execute an ordinary write. Checks and checked acknowledgements use the existing-host opener without creating a host, owner or key. Conditional input requires the current connection and checks at queue entry and immediately before its first master write, including after an EAGAIN yield. A mismatch reports `PTY_HOST_STALE_REVISION` and "This input was not sent." Once any bytes have been accepted, later failures remain uncertain; Aya never resends them. Lost conditional-write acknowledgements also feed B4's existing uncertain-input notice.

This stage changes JS-host bytes and will use the existing B3 handover for a compatible owner-backed host, or the #219 question for a destructive legacy migration. It adds no rule/policy module to the pinned host graph and changes no native-owner source. The new primitives do not yet enable user rules, alter team delivery or claim the worker/coordinator contracts are complete.

Local macOS arm64 evidence includes same-generation unbroadcast output, deliberately pending parser work, stale/current composer ACKs, resize/recovery/restore invalidation, old-host refusal without unfenced fallback, and a real host rejecting stale input while current input arrives exactly once. The real core's 1 MiB blocked-input fixture additionally queues a conditional write, changes the revision before it can write, and proves refusal with zero trailing bytes while resize and another pane remain responsive. A deterministic adapter fixture covers the narrower EAGAIN-before-first-byte race and a partial-write continuation that must not be mislabeled as not sent. Node and Electron stage results are recorded with the stage review; Linux native execution remains a CI gate, with these contracts added to its existing job.

The selected revision/parity/read-only/hash contracts pass 34/34 in Node 26.10. The real-host and two real-core large-input variants pass 3/3 in Node and 3/3 in Electron 43.5/Node 24.19. Existing core handover, replay metadata, crash recovery, screen proof and controller lifecycle regressions pass 56/56 in Node. The final combined revision and existing-regression selection passes 90/90 in Electron. These are stage checks, not a final whole-suite or GUI claim; user rules and delivery are not wired yet.

## Stage 2a - unused user data loader

I added data-only parsing and bounded private-directory discovery without activating it in main. The loader shares PR1's bounded strict JSON parser; it never constructs a user RegExp. It enforces the closed per-set envelope, collision refusal against every built-in ID, cross-file uniqueness, combined 256 authored and 128 effective rules per agent, and specific-before-generic order within the separate additive user layer. Syntax compilation still belongs to the worker, so a structurally valid `(` remains data here.

An absent/empty directory creates nothing. Discovery checks at most 256 directory entries, refuses unknown JSON filenames and ignores non-JSON editor files. No-follow/nonblocking descriptors, exact owner/mode/type/link checks, 64 KiB-plus-one reads, and descriptor/named inode/metadata checks guard against unsafe types and accidental changes. The directory device/inode recheck before/after the candidate is also an accident guard, not a race-proof directory identity guarantee; ancestor ABA can select another same-user rule file, which still receives every file check. This is a bounded candidate read, not activation: the reload coordinator must still invalidate epochs and confirm stability before publishing intentional deletion.

The new loader and existing bundled-data selection pass 67/67 in Node and 67/67 in Electron on macOS arm64, including exact valid byte/count boundaries, bounded growth, wrong UID/mode, hardlinks/symlinks/FIFO, replaced directory/file, and a main RegExp-construction trap. A deterministic same-user ancestor-ABA test records the accepted boundary: a replacement private additive file can be read, but an unsafe replacement file is still refused. No watcher, worker or live policy uses the loader yet; package, reload and GUI acceptance remain later stages.


## Stage 3 - unused guarded worker runtime

The main-owned runtime never compiles a user pattern. A fresh worker receives the bounded manifest, compiles/evaluates its patterns and returns only first-match IDs/kinds/regions/UTF-16 offsets. Main validates every result against its private manifest copy and its request before returning evidence. It sends only region text to evaluation, no command, environment or replay history. A missing manifest starts no worker and performs no worker IPC. No provider, control, delivery or explain consumer uses this stage yet; additive policy and host revision coordination remain a separate stage.

Each candidate has one parent monotonic2s initialization budget, including waiting for an old worker to terminate. Every actual dispatch has a parent100ms absolute active budget; valid replies at/after their deadline are refused even when the timer callback has not run. Timer callbacks recheck the clock. Active/compile overruns and malformed replies terminate the thread and quarantine the digest; later state polling cannot restart it. Changed data can recover, after confirmed old-worker termination. Epoch invalidation/dispose releases all callers and ignores old worker messages.

Queued work is limited to25contexts,16MiB aggregate UTF-8 region text and4MiB per request, with a1s end-to-end budget. Scope binds the future coordinator's host revision, caller and pasted exclusion, so distinct contexts for a pane do not borrow one another's result. A newer queued request replaces only the same context. Dispatch requires enough remaining end-to-end time for its full100ms active allowance; aging under healthy load is refused per request without quarantining a good digest. The later coordinator must supply and fence that opaque identity against the actual host snapshot; this runtime alone does not establish host freshness or authorize input.

Focused tests cover real finite-ambiguous/nested/Unicode-folding catastrophic expressions, main heartbeat responsiveness, actual thread termination, reload compilation stalled in a distinct real worker, valid replies at absolute deadlines before timer dispatch, queue recovery without file edits, copied manifest/request data, cross-scope isolation, malformed output and disposal/epoch races. Compilation spies reject user RegExp construction in main. No native-owner or GUI job belongs to this unused stage; packaged worker loading, 25-pane measurement and policy/control integration remain later acceptance gates.

Stage3 focused evidence: TypeScript build plus39/39 loader/worker unit contracts in Node26.10 and39/39 in Electron43.5/Node24.19, no native-owner/GUI job. Four separate compiled guard-removal checks fail their exact regression: accept late evaluation, accept late initialization, coalesce different caller/exclusion scopes, omit actual thread termination. Compiled bytes were restored and the focused suite passed again. These tests do not claim integrated policy/conditional-delivery behavior or packaged worker support yet.
