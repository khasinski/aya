# In-memory terminal-host authentication - rework of #231

I propose this rework from `pty-host-socket-auth` at `d7cda55c`, on branch `pty-host-auth-memory`. Justyna chose the in-memory secret on 2026-10-16. This note precedes product changes. Local user rules remain a separate PR; there is no remote-rule channel in the current plan.

## Authority and storage

Main creates a random 32-byte terminal-host capability in memory only, after the existing creation guards prove that a new host may start. It gives a new host its copy through inherited FD 5, with the current exact-length/type/deadline checks. The native-owner key keeps its existing separate in-memory/FD 3 path. Neither key goes in argv, environment, logs, registry, checkpoints, tickets or a persistent file. I will remove persistent capability creation/reading and the `pty-host-auth/key` dependency; an old development-build file is ignored and never used to adopt a host. Native-owner source and binary bytes do not need to change.

Normal application RPCs, status, events, reads, writes, kills, handover announcement/claim and owner continuity remain behind the existing authenticated transport. The only pre-authentication addition is a closed, bounded **announced-ticket redemption handshake**, not an application RPC path. It can reveal credentials only for a live announcement and its nonce. Ordinary missing/wrong proof still receives no unauthenticated status; retained private records and the verified kernel peer remain the authority for fallback questions and stop targets.

The main-owned client lends its in-memory capability to its short-lived read-only observer. That observer uses the same authenticated opener and never starts a host, owner or key. No key in this main means an unreachable/refused state answer, with no disk lookup or implicit adoption. Helper/test clients must receive authority explicitly in memory or through an inherited pipe, rather than recover it from a file.

## Announced ordinary quit and next launch

1. After all existing quit vetoes/background-work questions have succeeded, and before disposing the main client, normal quit makes one bounded announcement to its already-authenticated surviving host. It does not start/connect a missing host just to announce. It uses a fresh 32-byte nonce and the current host's PID plus kernel start identity. One parent-owned monotonic two-second deadline covers reservation, private-file publication and activation. A failure does not kill panes or delay quit indefinitely; it records that continuity was not prepared. Host authorization expires by monotonic elapsed time within at most 120 seconds of reservation; the serialized wall deadline is also checked, but clock rollback cannot extend host authority.
2. Main atomically publishes a 0600 nonce-only ticket in AYA_HOME, retaining B3's bounded no-follow/nonblocking, owner/mode/type/link/size checks and read-once deletion. Publication must use non-main-blocking I/O, not the current synchronous open/write/fsync/rename helper. Timeout returns without waiting for stalled I/O. Late completion is fenced by attempt identity and cannot activate an expired/revoked window; cleanup deletes only that attempt's nonce/inode, never a successor ticket. The host first reserves a **non-redeemable** slot, with an ordinary-quit activation deadline of two seconds, and activates only after successful publication and an authenticated in-budget commit. A late file without activation is inert even if cleanup/revocation cannot reach a closing host. An activation whose reply is lost is revoked where possible and never automatically reissued. The closed versioned ticket distinguishes ordinary reuse from a planned update. Ordinary quit does not freeze PTY reads, capture a checkpoint or change normal background-work semantics.
3. New main consumes/deletes the ticket before its normal host probe. It checks expiry and the socket peer's PID/start against the ticket before presenting the nonce. Redemption binds its reply to the nonce transcript, the old host instance/identity and the new main's kernel PID/start; the server reads the latter from the socket, never trusts request-supplied PIDs. The nonce holder can verify a bounded response from the selected host. Credential bytes remain in main/host memory and the local stream, never in a logged request/response.
4. The host atomically consumes the window and reserves the first valid recipient identity. Wrong nonce closes the window; a second request, expiry or unannounced request refuses. The host transfers its capability once. The new main then completes the ordinary authenticated proof and obtains the owner key/validated inventory through the existing authenticated owner-continuity path, once it owns the principal. A lost redemption reply is not retried as a second credential transfer: recovery falls back conservatively.
5. Credential transfer does not evict a living principal. If old main is still alive or its identity is unknown, the existing authenticated `principal busy` response applies: open the window, keep input disabled, retry under the existing ten-second budget, and never ask a destructive restart question for busy. Only proof that old main is gone allows the new principal to serve RPCs and complete continuity. If the budget expires, a later explicit attach may retry; it cannot create a host. The prior main and new main are never simultaneously served as distinct principals.
6. Successful adoption permits a later normal quit to announce a new independent nonce. An authenticated completion ACK from the pinned recipient moves claimed -> owned/rearmable **only after validated owner continuity**, not merely transport proof or EOF. A duplicate completion ACK is idempotent for the exact attempt/recipient. Failed, expired or lost-reply attempts cannot obtain another credential transfer through repeat quit, polling or EOF; an unavailable transfer stays unavailable until normal consented recovery/replacement. Cancelled quit removes only its own ticket/announcement, subject to the commit ordering below.

Planned B3 updates use the same credential-redemption primitive before normal authentication and checkpoint claim. **Both paths reserve the exclusive purpose/attempt slot before either ordinary publication or B3 preparation/freeze.** B3 retains its overall preparation deadline (at most 120 seconds); ordinary quit has the tighter two-second publication/activation deadline. A losing reservation performs no freeze/publication; its cleanup cannot cancel the winner. Their existing read/write barriers, process eligibility, display/core escrow, old-JS-exit proof and #219 fallback remain in place. An unchanged host needs ordinary reuse; a changed host still uses B3 to start the successor with both keys through inherited pipes. Keys never enter the checkpoint. Sharing the nonce window avoids two competing tickets or an unauthenticated exception for general `handover-claim`.

Reservation, activation, cancel and redemption have host-serialized state transitions. Cancel before redemption commit wins => no credential release, the old reader resumes if B3 had frozen it, and any late publisher removes only its own inert ticket. Redemption commit wins => the recipient stays consumed/pinned; old-main cancel/timeout cleanup cannot undo it, resume a committed old-reader path or rearm the slot. No asynchronous receipt/file operation may expose an intermediate redeemable state. The credential response is issued only after that atomic commit. A new-main connection failure after ticket consumption and before redemption preserves processes and reaches consent fallback, never implicit start/signal.

## Unannounced loss, compatibility and safe refusal

An unannounced main crash or force quit leaves no ticket and gives the next main no authority to adopt. The existing host and pane processes remain running. Main uses #231's retained-inventory/identity-bound #219 question, one verified single-PID SIGTERM and bounded gone proof, with B2 survivor consent as needed; Cancel preserves them. There is no generic create-host catch on authentication failure and no unauthenticated inventory request to a new host. A missing, unsafe, expired, consumed, wrong-host or unreadable ticket never authorizes a stop or automatic replacement.

A crash after a legitimate quit announcement can leave that already-announced short window open until its deadline; the host cannot know whether the announcing main's final exit was graceful. The distinction is whether an authorized quit announced the transfer, not an unprovable exit cause.

Pre-auth legacy v0.12.0 hosts retain the strictly bounded, identity-bound read-only size/count migration probe and #219 question; reply data never sets the signal target. An older authenticated development host without this redemption protocol is not adopted through its old persistent key. It goes to the same safe refusal/consent path. That old host's existing disk key remains an exposure while it is alive: this new main ignores it but cannot retroactively revoke it. Deleting old artifacts is not part of this design and must not be used to pretend a surviving old host has the new boundary. Older mains cannot authenticate to a new host without its capability, and no general RPC is dispatched for them. Their existing fallback UI varies by build; this change cannot retrofit an older executable. Registry protocol metadata stays compatible with #231's legacy discrimination and creation guards.

B4 automatic JS recovery continues when this main started the host or adopted both keys through a real announced transfer. An unannounced new main has neither key and gets no automatic recovery/adoption. Principal busy, shutdown grace, read-only authenticated state, uncertain-input/no-retry, exit-ACK and F11 native-owner retirement behavior remain acceptance gates. The host's changed JS identity uses B3's one-time planned handover or the existing consented fallback; owner bytes stay unchanged.

## Exposure stated plainly

This removes the persistent readable capability and the ability of an ordinary agent to recover it merely from configuration files outside an announced transfer. It does not provide an OS sandbox against root, process-memory inspection, a compromised authorized main/host, or an unsandboxed same-user process during an announced transfer. A same-user process able to read AYA_HOME can steal the nonce during its at-most-120-second window and race to become the one recipient, then obtain owner continuity after the old principal exits. Kernel PID/start binding prevents replay to another process instance; it does not prove that the executable is Aya or prevent the first thief. The native-owner secret remains out of persistent storage. I must qualify **the owner documentation itself** (`docs/pty-owner.md`, its configuration-reader exclusion), alongside current auth docs and the PR, with this announced-transfer exception and the process-memory-inspection limit; its existing exclusion cannot remain unqualified. No native protocol or binary change is needed for that truthful boundary.

## Stages, tests and effort

I estimate **14-22 hours of implementation, test adaptation and focused review work**, plus the serial full validation runs (roughly one hour per complete Node/Electron/package/affected/whole cycle, longer if a baseline comparison is needed). This is an engineering effort estimate, not a promise about review or CI turnaround. The main risks are pre-auth redemption accidentally widening RPC access, repeated-quit window lifecycle, quit cancellation and B3 ticket ordering. I propose these reviewable stages:

- **Memory/bootstrap and redemption primitives (4-6 hours):** remove persistent authority, build the bounded transcript/nonce/peer-bound one-use exchange, and pin no announcement/wrong nonce/expiry/duplicate/lost reply/recipient identity. Test fragmented, oversized, stalled and malformed frames before any RPC/event. Assert no owner-byte change.
- **Quit/relaunch and B3 integration (5-8 hours):** two-second bounded quit announcement, exclusive versioned ticket ownership, early redemption, one-principal takeover/ten-second busy wait, read-only observer memory authority, owner-key continuity and safe unannounced fallback. Real processes test old main kept alive, window visible/no question/no signal, takeover after old main exits, repeated ordinary quits, cancelled quit and app quit during waits. B3 planned host replacement still preserves child PIDs/display/history. Main/host SIGKILL without announcement requires consent and never silently spawns or adopts.
- **Fixture/package adaptation and final evidence (5-8 hours):** replace persistent-key fixtures with explicit memory/pipe authority without weakening refusal assertions; cover legacy v0.12.0 migration and native-owner retirement. Both runtimes, npm, lint, staged package, affected and whole offline GUI run with shutdown=0/workers=1/default ceiling. Refresh the authenticated 25-pane continuity/recovery latency, RSS/CPU and cleanup evidence if timing paths change. Document current evidence separately from historical persistent-key results.

Every status/read/write/kill/handover/continuity path must remain inaccessible without completed ordinary authentication; the single dedicated redemption handshake grants credentials but no general RPC dispatch. Tests keep no-start/no-unlink/no-signal checks, pending-connection/frame/deadline bounds, principal busy versus real proof failure, existing startup shutdown grace, B3/B4 same-PID and exit outcomes, observer unknown/not-running answers, and package authority inheritance. Additional deterministic acceptance cases cover blocked publication and late completion, clock rollback/forward, simultaneous distinct-process redemption (one recipient), replay after a successfully rearmed window, cancel/publication/redemption interleavings, losing ordinary/B3 reservations and failed B3 resume without cancelling a winner. A valid old disk key must be ignored, fresh startup must create no capability file, and consumed-ticket/pre-redemption connection loss must preserve processes without starting or signalling anything. No network, push, merge or production change is part of this work.

## Stage 1 - unused credential-window state

I added an unused `HostAuthTransfer` state machine and a memory-only capability constructor, without replacing current main/host behavior yet. It reserves the exclusive purpose before caller I/O/freeze, activates within its monotonic budget, commits one recipient before returning a copied credential, and refuses all subsequent redemptions. Wrong nonce/attempt seals the active window. Issuer cancellation after redemption reports committed and cannot undo the recipient; it has no PTY-reader or lease operations. Rearming requires the exact recipient's authenticated completion against the latest owner-continuity manifest receipt. Mere transport proof, EOF, expiry, failed attempts and old issuer cleanup cannot rearm it.

Local macOS arm64 build and selected primitive/B3-window tests pass 28/28 in Node 26.10 and 28/28 in Electron 43.5/Node 24.19. Cases cover no announcement, inactive reservation, one winner among competing logical calls, wrong nonce/attempt/peer, exact deadline/clock changes, competing purposes, cancel/commit order, stale replay after rearm, receipt and process-instance binding, and disposal. These are pure-state tests: distinct real-process claimants, transcript transport, stalled/late filesystem publication, old-disk-key ignorance in the real client, ordinary quit and B3 integration remain acceptance work for later stages. Native owner source is untouched; the rebuilt local executable still has SHA-256 `2d93372d8249dd1c3a7593d0869f863fdb53971c36076c71dad9939a5a3e4109`.

## Stage 2a - unused asynchronous ticket storage

I added version-2 nonce/host-identity ticket storage using asynchronous filesystem operations. The caller supplies the one parent monotonic deadline that starts before reservation. Timeout/cancel returns without waiting for stalled open/write/fsync/rename, and every subsequent phase checks the deadline again; late completion can only clean that attempt's own inode. Publication grants no host authority: the still-unused integration must reserve a non-redeemable slot and activate only after in-budget publication. Ticket errors are fixed text and cannot disclose malformed payloads through parser error messages.

Each attempt uses `pty-handover.<attempt>.json`, with a separate random temporary name for atomic publication. The filename must match the closed payload's attempt. Different attempts never reuse a ticket path, keeping late cleanup away from a later ticket; bounded startup discovery and owned-nonce cancellation still belong to integration. Reads are nonblocking/no-follow, exact owner/0600/single-link regular-file checked, capped at 1024 bytes with a 1025-byte bounded buffer, and consumed once after identity/metadata checks. Both the wall ticket expiry and host monotonic expiry remain mandatory.

Storage and transfer-state contracts pass 23/23 in Node and 23/23 in Electron on local macOS arm64. Fixtures block open/fsync/rename, exercise cancellation and late completion before a delayed timer callback (including final close), retain a later attempt while cleaning the old one, prove main heartbeat continues during blocked fsync, and cover exact byte bounds, growing files, FIFO/symlink/hardlink/owner/mode/changed-inode refusal, once-only read and safe fixed errors. Every successful operation also faces the parent deadline/abort check after its final await; stalled fixtures assert a generous elapsed upper bound. Consumption becomes irrevocable once unlink is submitted: a timeout can consume a ticket without returning its nonce, and integration must use conservative fallback rather than retry or promise preservation. No main quit/startup or product host uses this storage yet; no claim of completed transport, key removal or end-to-end continuity is implied.

## Stage 2b - unused dedicated redemption transport

I added a single-frame nonce redemption exchange, separate from application RPC and the normal capability proof. The client checks the socket kernel host identity against the ticket before presenting any nonce. The server binds its one recipient to the kernel client PID/start and commits it before releasing the capability. Its response has a domain-separated HMAC under the one-use nonce over purpose, attempt/deadline, client/server nonces, instance, both peer identities and the credential. A client validates that proof before returning credential bytes. A wrong nonce (including malformed nonce data) or a conflicting active reservation closes that transfer window. Replaying a lost credential response cannot obtain another release or rearm the slot.

Each direction accepts one closed frame of at most 1024 bytes under a five-second whole-exchange deadline, with checks independent of timer callback ordering. Coalesced trailing bytes are refused before redemption. If a valid frame arrives first and an RPC follows in a later chunk, the valid redemption may succeed; the later bytes never reach an application parser or receive another response. Successful server writes close their socket after flushing, with a bounded close fallback. The future product acceptor must share the existing aggregate 32-pending-connection cap, rather than give redemption a second budget or dispatch application messages on its socket.

The redemption/state/existing-auth selection passes 37/37 in Node and 37/37 in Electron on local macOS arm64. Two real separate child processes use actual kernel peer identities and race the same ticket: exactly one receives the expected credential digest. Tests also cover replay/binding/field tampering, host mismatch with zero nonce bytes sent, fragmented/max-size frames, oversized and coalesced trailing requests, a later-chunk RPC with one valid credential response/no remaining parser, a lost reply after committed consumption, and real five-second client/server stalls with bounded elapsed assertions. These helpers are still unused by the product listener/main. Global pending-budget routing, ticket discovery, ordinary quit, persistent-key removal, real B3/B4 continuity and package/full validation remain future integration stages.

## Stage 3a - shared acceptor routing

I added optional redemption routing to the normal socket acceptor. Both kinds share the existing 32-pending-socket budget and one absolute five-second accept deadline, including the initial-frame wait and subsequent proof; classification cannot reset either budget. A successful redemption returns a distinct transferred result and closes its socket, never authorizes a main principal or reaches application attachment/events. The product host handles that result explicitly; enabling a real host transfer slot and control requests still belongs to the next stage. Existing normal proof uses this acceptor now, but the product has not yet enabled redemption or removed its old persistent-key path.

The routing/previous transport/build-hash selection passes 26/26 in Node and 26/26 in Electron on local macOS arm64. New tests prove shared connection saturation, zero application events/dispatch on redemption, normal proof on a later separate connection, and old-principal same/unknown refusal followed by proven-gone takeover. A timed split opening/proof case pins the single overall deadline. Deterministic valid-proof, authorization-observer and final-handoff cases advance the same monotonic clock past the original accept deadline before the timer can fire; each must refuse rather than attach. The pinned graph explicitly adds only the transfer/redemption core modules; rule policy/data remain outside the host hash. No native-owner source changes, main quit wiring or full-gate claim is part of this stage.

## Stage 3b - authenticated transfer controls

The real host now owns a credential transfer slot and enables the dedicated redemption route. Only an authenticated main can reserve, activate, cancel or complete a window. Planned activation additionally requires the matching published B3 core checkpoint and nonce announcement. Ordinary reservation refuses an already active core handover; an ordinary reservation also prevents a competing B3 freeze. Credential cancellation never aborts the independent core handover or closes the owner lease.

An authenticated, attempt-tagged owner-continuity response binds its exact manifest digest to the committed recipient. Completion is accepted only after that recipient validates continuity and acknowledges the digest; transport proof alone cannot rearm the slot. Real-process tests consume a nonce ticket after the old main exits, authenticate with the redeemed capability, validate the same owner/child identities, reject premature completion, and complete/rearm once. Closed control envelopes and the existing pre-auth all-RPC refusal test include every new verb.

This remains an intermediate integration stage: main still uses its previous persistent-key path and does not automatically publish or redeem tickets. Existing untagged B3 calls remain compatible only while the transfer slot is empty; the upcoming main/B3 integration must reserve before freeze and remove that transitional allowance. Tests use explicit in-memory credential injection, not a new automatic adoption path. Local transfer-controls/auth-integration/controller tests pass 11/11 in Node and 11/11 in Electron; existing real B3 natural-exit, replay-ACK, cross-runtime and bootstrap regressions pass 16/16 in each runtime. No native owner source or binary change is part of this stage.

## Stage 3c - bounded ticket discovery and cancellation

Startup can now locate one version-2 ticket using only the fixed attempt filename grammar, a private current-user 0700 home, at most 256 directory entries and the caller's single monotonic deadline. It refuses multiple candidates without choosing or consuming either; an absent ticket returns no transfer. Existing persistent key files, legacy B3 paths and temporary filenames are never considered authority. The selected ticket still passes every bounded, private-type and once-only-consumption check from stage 2a. Directory identity rechecks are accident guards, not protection against a same-UID writer that can already read the ticket.

Cancellation checks the attempt, nonce and opened/named inode before unlinking its own private file, and can clean its expired attempt. It leaves another nonce/attempt and unsafe files untouched. Ticket unlink remains irreversible once submitted, and does not cancel the independent host slot. This storage helper does not yet change startup, quit or B3 behavior. Discovery/cancellation and existing storage tests pass 18/18 in Node and 18/18 in Electron locally, including ambiguous candidates, old-key ignorance during discovery, entry cap, symlink/mode refusal and deterministic final-close/final-probe deadline checks. Product-wide old-key ignorance is still pending main integration.

### Stage 3b cancellation follow-up

A reviewer found that the existing B3 cancellation API could resume the core without revoking its matching active credential announcement. Authoritative core abort now synchronously revokes that uncommitted planned window before readers resume or asynchronous escrow cleanup begins, including expiry/failure aborts. This callback runs only after the core's peer and irreversible-commit checks. It cannot cancel an ordinary window or undo a claimed recipient; the independent B3 detach boundary is unchanged. A real old-main/new-main test calls only the existing B3 cancel API, then proves later redemption releases no credential and the same pane remains usable. Transfer/controls/core-controller/discovery contracts pass 25/25 in each runtime; the valid-ticket entry-cap fixture also verifies refusal leaves its ticket unconsumed.

## Stage 3d - continuity after the last owner idles out

A JS host can survive its last pane and the native owner's idle shutdown. An announced recipient still needs to complete its credential transaction without inventing or starting an owner. Attempt-tagged continuity therefore has a closed empty variant: zero core/pending-spawn/restored records, no runtime opening or stopping, and no retained owner record. It returns the host's in-memory future-owner credential and an exact empty-manifest receipt; the receiving main must independently require the authenticated host's version to report zero panes and no owner. Unreadable or retained owner metadata refuses this variant. Existing live-owner continuity keeps its original format and complete inventory validation.

A shared validator checks the closed envelope, host instance, bounded bytes and manifest receipt before exposing either live or empty continuity. Local controls/continuity tests pass 13/13 in Node and 13/13 in Electron. The real empty case starts with a pane, closes it, waits for the original owner to retire, transfers after old-main exit, refuses an unreadable retained record, completes/rearms with no owner creation, and verifies the owner record remains absent. Main startup/quit and persistent-key removal remain the next integration stage; this is not a claim that product relaunch already uses the new format.
