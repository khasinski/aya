# Owner-backed panes - B2

I implement the [accepted B2 plan](pty-host-handoff.md#b2---spawn-and-reap-new-panes-through-the-owner). I replaced the JS host's node-pty spawning with an owner-backed IPty adapter. Main still prepares command, argv, environment, cwd and resume selection and evaluates agent screen rules. The JS host still owns VT, replay/search, OSC parsing and the existing preparation flight. The native owner forks, owns the master, resizes, signals process groups and reaps children. No rules, sessions or VT implementation moved into native code.

This branch depends on #224's slim host/content identity, B1's owner/bridge/packaging, and the restart-question fixes. It does not implement planned handoff/checkpointing (B3) or automatic crash recovery (B4).

## Ownership and failure behavior

The private `AYA_HOME/pty-owner/record.json` records the owner's PID/start identity, executable/content hash, random process instance, current JS reader identity and bounded pane inventory. It contains no authentication key, command, environment or descriptors. Main retains a random key in memory and passes it to the JS host through an inherited private descriptor; the JS host starts the owner with another inherited pipe. The native socket lease and file lock exclude duplicate owners/readers. A liveness read failure refuses takeover.

The IPty adapter consumes a CLOEXEC master duplicate as a paused TTY stream, installs the core sink before resuming reads and decodes split UTF-8. It explicitly sets the master nonblocking. Input writes keep their own ordered queue; backpressure yields while polling writability at 5 ms intervals, so a large paste cannot block the JS event loop. Resize calls TIOCSWINSZ directly on the master without waiting for input, then updates the native owner's geometry record. Write acknowledgement follows actual PTY acceptance, including partial writes; a rejected renderer write visibly reports that input may have been partly delivered and is never automatically retried. An explicit false result reports that no input was delivered. Kill interrupts blocked input and targets the recorded native generation. New spawns for a retiring pane ID wait for its previous exit acknowledgement.

Real exit status comes from the native parent's waitpid, independently of the TTY read stream. The adapter drains output before emitting exit and acknowledging the native record, with node-pty's existing 200 ms post-exit ceiling. Native cleanup kills same-group descendants before releasing the leader's PID/PGID. An explicit destructive shutdown waits for the owner to exit and removes only its matching registry instance. Empty owners retire after pending spawns and exits settle; a lost spawn acknowledgement retains uncertain inventory and blocks retries instead of assuming no child exists.

The native receive bridge separates the idle first-byte deadline from the bounded remainder-of-frame deadline. A frame starting just before an idle poll expires therefore cannot be misclassified as an idle timeout midway through its header. Idle receive timeouts leave the connection usable. Malformed error frames reject outstanding requests before closing the connection; they cannot remove a request's timer and leave its promise unresolved. JS idle shutdown is disabled while an owner is incompatible or has disconnected inventory, including an uncertain spawn with no known PID. The absence of an acknowledged pane record does not authorize killing its native process.

An old, pre-owner host follows #219's question-and-restart before migration. Its children are never reparented. A live incompatible owner also requires confirmation before its processes stop. Cancel leaves the original processes and inventory intact. The host content identity includes the actual owner and bridge bytes as well as the existing JS/runtime dependencies; version-only updates continue to reuse the host. B2 still uses a confirmed destructive restart for changed JS-host core or runtime; preserving those panes during an update belongs to B3.

If the JS host dies, surviving panes remain visibly disconnected, with their owner inventory retained. They are neither marked stopped nor silently respawned. A replacement JS host can inventory a compatible owner using the retained in-memory key, but B2 deliberately does not adopt masters or reconstruct a screen. Without a compatible authenticated owner, pane kill refuses and explicit terminal-host recovery must ask about all work that will stop. A refused Restart terminal, Close terminal or Close project shows a window alert naming the affected panes and reasons and keeps their visible records. Restart refuses before requesting another spawn. Input, paste and snippets are disabled while disconnected; the terminal explains that input is disabled. Hold remains unknown until a real applied screen exists; busy retains its existing fail-open behavior. Input with an uncertain outcome is not replayed.

Before sending SPAWN, JS persists the pane ID and a random intent generation, also marked uncertain. This generation identifies the request; the native pane generation is assigned only after fork. A successful reply becomes a pane record before the matching intent is cleared; an explicit native rejection clears only that request's intent. JS death before a reply leaves an uncertain entry even if the native owner then dies. Only an authenticated complete inventory or a proven orderly native shutdown can resolve an intent without a recorded child identity.

An owner death also preserves its inventory, even after the last JS reader exits. It cannot silently turn into an empty replacement owner. Diagnostics recovery lists pane names/PIDs and asks first; Cancel keeps the inventory and blocks spawn. After confirmation, recovery verifies the recorded leader identity, enumerates its group members, measures each member's PID/kernel start identity, rechecks the leader and persists that bounded member inventory before any signal. Unknown identity or more than 32 members refuses recovery. Each member is signalled individually; the non-parent bridge never sends a destructive signal to a numeric group. Linux opens a pidfd, rechecks identity and group membership, then uses pidfd_send_signal against that process instance; an unsupported syscall fails closed. macOS rechecks identity immediately before kill(pid). macOS normally allocates PIDs in sequence up to 99999 before wrapping, so exact PID reuse in that short window requires wraparound, but this is not a kernel guarantee: the remaining check-to-kill race is explicitly accepted by the platform policy. A mismatch or unreadable identity is never deliberately signalled.

Recovery relists the group after signalling and retains surviving, newly appeared or unverifiable processes and their reasons. A retry uses its persisted member identities rather than inventing replacement targets. If a leader exited before a member inventory could be established, or identity cannot be confirmed, Aya retains the entry and reports which listed processes were not stopped; the user must stop those processes before recovery can complete. A non-destructive pidfd capability probe makes an unsupported Linux kernel/emulator refuse explicitly. Normal shutdown continues to use the native parent and its unreaped-child PID reservation. This adds no automatic native crash-reaper or reparenting.

The F3 native regression deterministically makes the target exit or acquire a different kernel start time during the group check, then asserts that no signal is sent. Linux additionally asserts that successful signalling uses the opened pidfd and closes it on every path. The real survivor test includes a HUP-ignoring descendant and checks both processes after confirmed recovery. In local x64 emulation, pidfd signalling is unavailable: that run must verify refusal and retained live inventory, rather than pretend recovery succeeded. The native Linux CI job sets `AYA_OWNER_EXPECT_PIDFD=1`, making lack of successful pidfd recovery a failure there.

The owner has no output ring: unread bytes remain in the kernel queue, and a child eventually blocks if no JS reader drains them. Already-read screen/history can be lost after a crash. An unexpected native-owner crash may close the last master and HUP children before a question is possible; Cancel cannot restore already-lost work. The #204 uncaught-error guard remains on the JS host, and the watched replaceCells crash is unchanged.

## Validation and measurement

The adapter/core contracts exercise ordered input and independent resize, UTF-8/output-before-exit, actual exit status/signal, duplicate spawn/readers, uncertain spawn acknowledgement retention and generation-safe retirement. The 1 MiB regression goes through real pty-core spawn/write/resize, asserts native parentage, keeps the paste blocked while resize and another pane answer, and verifies the full count/hash with an end marker and no trailing bytes. A renderer e2e pastes through xterm and real IPC/core, kills the native owner while the write is pending, and requires the partial-delivery warning, one write attempt and no unhandled page error. Existing preparation tests retain cancellation, timeout, disconnect and queued-write coverage. The pinned JS import graph and native include-boundary test prevent rules/sessions/VT from entering the native core. Migration e2e uses real child processes and verifies both Cancel and confirmed recovery for legacy and incompatible owners.

At review-fix commit `b1f0690f`, full `npm test` passed with 6,801 pass, 0 fail, 147 skipped and the existing registry TODO. Recovery contracts include a real HUP-ignoring child after owner SIGKILL, Cancel, blocked duplicate spawn, a deliberately mismatched kernel start identity, and confirmed cleanup followed by a new generation. A real host death between native spawn and its first JS response must emit disconnected rather than stopped. Fourteen focused Electron e2e passed with `AYA_E2E_PTY_SHUTDOWN=0 --workers=1`: real incompatible-owner restart/close-pane/close-project refusals, disabled disconnected input/paste, explicit legacy migration consent, confirmed dead-owner recovery, restart-background-work and restart-busy-panes. The 25-adapter resource regression verifies both native master and JS reader FD counts return to their baselines after kill; acknowledged native generation records may remain without open masters. The final whole e2e result is still pending.

The comparison runner uses the same Electron runtime and the same offline workload against built #224 and B2 checkouts:

```sh
node scripts/measure-pty-backends.cjs /path/to/built-224-checkout
```

Each backend runs 25 idle panes and 25 active panes separately in disposable homes. An active child writes 4 KiB plus a monotonic timestamp every 20 ms; the sample includes rolling-buffer warmup. Input latency is 100 command/reply round trips, including the child and PTY, rather than a write-call duration. Output latency runs from the child's monotonic timestamp to the main client's data callback. Three RSS samples cover the JS host, the native owner when present, and a headless main-side client. Child RSS, renderer memory and kernel PTY buffers are excluded. Raw observations remain in ignored `test-results/pty-backend-comparison.json`; local samples are not production bounds.
