# PTY owner handoff - accepted delivery plan

I keep the accepted B1-B4 plan here from design commit `b70ad651` (`docs/pty-host-handoff.md`). The Phase A/A2 research and throwaway scripts remain in that design commit. B1, #224 and #227 are now merged; B2 starts on main `f8eab3d0`.

## Route B delivery plan

I propose four dependent PRs. This plan is documentation only; product implementation starts after the lead accepts its scope. Each PR builds on #224 (`7517f8b5`, then main after merge), goes to review and answers every finding. No push, merge, product rebuild/swap or release action is authorized by this plan.

### B1 - native owner, protocol and packaged feasibility

**Scope:** build a small native owner and supported SCM_RIGHTS bridge, without connecting normal Aya startup/spawn to them. Main's prepared command/argv/env/cwd arrive as data; the owner contains only PTY lifecycle, geometry, master ownership, process groups, waitpid and local protocol. Define bounded/versioned messages, peer authorization, pane generations, one owner registry/identity, exclusive JS-client leases, cancellation, shutdown escalation and acknowledged exit events. Socket EOF alone must not grant a new reading lease while the old client still holds descriptors. Owner identity must be independent of Electron/Node, with no integrity relaxation to hide signing changes.

**User change:** none; no normal product path starts or uses the owner yet.

**Done:** native/protocol tests on macOS arm64 and Linux x64 cover spawn/I/O/resize/kill/reap, partial/malformed/oversized frames, unauthorized peers, duplicate owner/client attempts, descriptor cleanup and failed attach. Kill/disconnect the client, let the child exit during the gap, then attach a new client: retain the real exit code/signal until acknowledgement, use a stable generation/event ID to deduplicate retries, show one logical exit, and do not resend an acknowledged exit as a new event. Include death before/after delivery/ack, natural exit vs kill races and no zombies. Preserve the A2 preexisting-unread-output barrier test. CI builds both binaries/bridge, bundles the executable outside asar, and smoke-tests the actual staged package under bundled Electron; macOS verifies nested signing and the distribution signing/notarization path, Linux checks linkage and package execution. Package output stays in disposable staging, away from prod and `release/`. Measure two packaged builds' identity, 1/25-pane owner RSS/idle CPU and FD cleanup; record actual numbers without inventing acceptance thresholds. Run `npm test`; existing startup/e2e remains unchanged.

**Risk:** native protocol/descriptor security, job control and signing/packaging can dominate the change. Do not start B2 until packaged execution on both target platforms works; an unsigned local C probe is insufficient evidence.

### B2 - spawn and reap new panes through the owner

**Scope:** replace the `pty-core.ts` node-pty lifecycle calls with an owner-backed adapter; preserve `IPty` behavior at its consumers rather than putting sessions/rules in native code. JS retains VT/replay/search and main retains spawn preparation/rule evaluation. Wire owner registry/discovery, input/resize ordering, preparation cancellation, process-group kill/escalation, natural exit and shutdown. A legacy pre-owner host follows #219's question-and-restart once before owner-backed panes are created; never attempt to reparent its live children. Planned seamless replacement and automatic JS restart remain for B3/B4.

**User change:** normal terminal/agent behavior stays the same; future panes have a stable native parent. First legacy migration asks before stopping existing work. Until reconnect is enabled, an unavailable JS host must stay visibly disconnected, with its owner inventory retained; never declare surviving panes stopped and silently respawn duplicate processes. Destructive recovery continues to ask first.

**Done:** adapter/core tests cover prepared commands/env/cwd, resume, spawn/kill/restart races, main disconnect mid-prepare, bounded preparation timeout and queued writes delivered once after spawn. Verify output/OSC carry, resize, all exit codes/signals and ordinary quit/background-work behavior. `npm test` and the entire existing e2e suite pass with `AYA_E2E_PTY_SHUTDOWN=0 --workers=1`, including boot-reused-host, opencode resume, restart-busy-panes, restart-background-work, team-busy and team hold specs unchanged. Add migration cancel/confirm and incompatible-owner question tests, explicit shutdown/reaping and duplicate spawn/owner exclusions. Measure 25 active/idle panes, input/output latency and owner/JS memory against #224; pin the native core boundary so rules/sessions/VT cannot drift into it.

**Risk:** matching node-pty spawn, signal, login-shell, cancellation and exit semantics across macOS/Linux. Losing a kill race can orphan a process; losing the inventory can spawn its duplicate. This PR must establish correct ownership and visible disconnected state without depending on B4's automatic recovery.

### B3 - planned JS-host replacement with a checkpoint

**Scope:** replace the destructive `pty-host-client.ts` restart path for compatible owner-backed panes. Gate input/spawn/kill operations, settle preparations and writes to a bounded deadline, stop old PTY reads, then drain already-read output through replay/OSC/VT before the final checkpoint with pane/event generations and an output byte-sequence boundary. Consume no further PTY bytes between that checkpoint and old-host exit. Stop the old JS host and confirm release/death before starting its successor, while the same owner keeps masters and children. Import the checkpoint, reconstruct full VT/parser state, replay/search metadata, OSC carry, original spawn records, queued input and pending exit acknowledgements, then release input. For input, require per-pane generation/sequence acknowledgements and deduplication, or a bounded pre-exit drain proving no write has an ambiguous outcome; abort planned cutover if that proof fails. Acknowledgement means bytes actually accepted by the PTY, not merely queued in JS, and import must never retry an already-delivered Enter. Keep PR 2's content/runtime hash as the JS replacement trigger; unchanged JS identity needs no replacement. Checkpoint format/version/size must be bounded and validated. An unsupported pane, legacy host, changed owner or failed restore uses #219's question before any process would die; Cancel preserves the surviving owner/panes.

**User change:** a planned update that changes JS-host core or Electron/Node keeps pane PIDs, display/history and pending work when compatible. An update changing only the version still keeps the host/panes, as in #224. The native owner itself still uses question-and-restart when it must change.

**Done:** full VT parity includes normal/alternate buffers, cursor/attributes/modes, partial control sequences and generation/composerSeen; do not substitute the lossy rule snapshot for a checkpoint. Unit/integration tests inject failure at prepare/checkpoint/old-host-exit/attach/import boundaries, plus partial writes and Enter reaching the PTY before its ack is lost, writes/resizes/kills during the barrier, unread output at the final checkpoint boundary, main disconnect, rollback/Cancel and duplicate owner/JS-host prevention. Add Electron e2e for version-only, rules-only, core-change and runtime-change replacements, asserting unchanged child/owner PIDs, planned display/search fidelity and no repeated input. A child exiting while no JS host is attached must retain its real status in the owner; the next host applies one exit and reconnect/ack retries never create a second pane exit. Exercise this end-to-end in addition to B1's owner-level test. Existing restart-busy/background/team-busy/hold e2e still pass, including destructive fallback questions. Run `npm test` and touched e2e on both platforms. Measure 25-pane full checkpoint bytes, peak memory, pause/reconnect latency and continuous I/O correctness; the earlier 27.3 MB fixture is not the full checkpoint measurement.

**Risk:** complete VT serialization and exactly-once application of input/exit events are the largest correctness risks. If restoration is not provably faithful, refuse the seamless path before destroying processes. Failed new JS startup must leave the owner and children alive for retry or a confirmed destructive fallback; no second serving JS host may overlap.

### B4 - automatic JS-host crash recovery (plan step 2)

**Scope:** detect an unexpected JS-host death, use bounded restart/backoff, acquire its released lease and attach to the same native owner. Reconcile inventory/generations and exit events rather than respawning children. This path has no guaranteed fresh checkpoint: accept loss of already-consumed screen/scrollback, use only unread kernel output and subsequent redraw, and keep hold fail-closed until a newly applied screen is known. Preserve existing busy fail-open semantics without treating that as permission to type through an unknown hold. If the old JS host dies after a PTY write but before its acknowledgement, classify that outcome as uncertain: do not automatically retry input or claim it was delivered unless generation/sequence evidence proves it. Expose/settle the uncertainty to the caller rather than duplicate an Enter; accepted screen/history loss is not input-retry permission. Do not add an owner ring or promise historical output recovery.

**User change:** after a JS-host crash, pane processes keep running and Aya brings their connection back automatically. A pane may have an empty/incomplete screen until redraw; agent/team delivery waits for reliable screen state. A planned replacement of a live incompatible owner still asks before stopping children. An unexpected native-owner crash has no equivalent guarantee: if the last master closes, the kernel may HUP the session before Aya can ask. A surviving JS client may retain a duplicate, but neither survival nor the lost parent's exit status is guaranteed; Cancel cannot undo work already lost. Report that failure honestly and ask before any subsequent action that would stop proven survivors.

**Done:** Electron e2e SIGKILLs the real JS host while a shell and busy/held agents run, then asserts a new JS PID, the same owner/child PIDs, pre-crash unread output and new I/O/resize, eventual redraw and no duplicate session/spawn. Exercise a child exiting during the no-host gap and after recovery, including exit-ack retry/deduplication and pane generation reuse. Kill JS after bytes reach the PTY but before the write ack; assert no replayed Enter and no false delivered result, plus the explicit uncertain outcome. Test native-owner SIGKILL with and without an attached JS client/master duplicate, distinguish proven survivors from dead panes and show no promise that Cancel can recover already-lost work. Test repeated JS crashes/backoff exhaustion, app quit during recovery, stale/legacy/incompatible owners and failed new-host launch; no restart loop, hidden surviving pane, dual host or promptless destructive recovery. Verify hold stays unknown before applied reconstruction and busy/hold/VT-status events recover correctly; run team and restart e2e, `npm test` and touched e2e on both platforms. Measure 25-pane recovery time/CPU/memory and behavior under kernel-queue backpressure; test that owner idle polling does not spin on unread PTY output.

**Risk:** recovering too early could send team text into an unknown prompt; replaying a stale pane identity could affect its successor. Lost screen/history is an accepted initial limitation, not a reason to invent a ready state or silently restart the child.

Across B1-B4, tests stay offline and use disposable homes/staging; TCP fixtures, if any, bind only `127.0.0.1` with port 0. Keep the #204 `keepHostOnUncaught` guard and leave the watched replaceCells crash untouched. Every deliberate destructive action retains #219's question first; an unexpected owner crash may already have stopped children before any dialog is possible. There is one owner and one active JS reader/host for each pane set; a retired host is not left running alongside its replacement.
